# 14 — Warn when a Chapbook variable is shadowed by a window global

Type: task
Status: closed
Blocked by: none

Chapbook exposes story variables to JavaScript by defining proxies on
`window`. `addStateProxy` (Chapbook 2.x `src/runtime/state/state.ts`; the
1.2.3 build does the same) **skips any name already truthy on `window`**. So
`location: 'cave'` works in a `{location}` insert, which reads state directly.
But every JavaScript context sees the browser's object instead: `[if location
=== 'cave']`, `[JavaScript]`, vars-section values and conditions, and insert
arguments. The story is silently broken. It isn't limited to `location`: the
same goes for anything truthy on `window` (`open`, `top`, `origin`, `Date`,
`Map`, …) and Chapbook's own window objects.

Came out of ticket 05's review. Ticket 05 settled that Chapbook still
_indexes_ `location`, `history`, `navigator`, `alert`, `prompt` and `confirm`
as story variables (option A). This ticket doesn't change that. It tells the
author why the variable won't work.

## Work

1. **New diagnostic** `chapbook-variable-shadowed-by-browser` in
   `shared/src/diagnostics.ts`, at Warning severity, disableable like the
   others.
2. **Trigger names**:
    - Every name truthy on `window` in Chromium, Firefox **or** WebKit (the
      union), from the generated list in item 4. JavaScript's own globals come
      along automatically.
    - Chapbook's own window objects: `engine`, `browser`, `now`, `passage`,
      `random`, `story`. These are Chapbook _lookups_: `addLookupProxy`
      (`src/runtime/state/state.ts`) creates a plain object on `window` for
      each root, so a same-named story variable is shadowed. Derive them from
      the roots of the built-in list in `chapbook-diagnostics.ts` (~line 90),
      **excluding `config`, `sound` and `trail`**. Those are created through
      `set`/`setDefault(s)`, so they're state-backed and proxied normally.
      Prefer an explicit exclusion set over a comment so a new root forces a
      decision.
3. **Check in the Chapbook parser**, on the raw name _before_ `js-parser.ts`
   filtering. Vars-section names go through the JS parser, so a variable
   named `Date` or `document` never reaches the index.
    - Fire only where the variable is **set**: vars-section names (strip a
      `(condition)` suffix) and string-literal `engine.state.set('…')` names.
      Skip computed names.
    - Fire at every place the variable is set, not just the first.
    - Dotted names (`location.x: 1`): check the first segment and underline
      only that segment.
4. **Generated list**:
    - `scripts/build-window-globals.ts`, run as root `package.json` script
      `build-window-globals`. Pin Playwright as a dev dependency.
    - The script launches Chromium, Firefox and WebKit on `about:blank`. It
      walks `window` and its prototype chain (`Object.getOwnPropertyNames` per
      level) and keeps names whose value is truthy, wrapping each read in
      try/catch. It takes the union across the three browsers.
    - It writes `server/src/passage-text-parsers/chapbook/window-globals.ts`,
      a sorted, committed `ReadonlySet<string>`. The file's header says
      "generated by `scripts/build-window-globals.ts`, do not edit" and
      records each browser's version.
    - Rewrite the file **only if the name set changed**, so a version-only
      header diff doesn't appear.
5. **Build wiring** (revised 2026-10-13): **don't** run the script during
   `package` or `prebuild`. Packaging shouldn't depend on three installed
   browsers. Instead:
    - Developers run `npm run build-window-globals` by hand and commit the
      result. The pinned Playwright version pins the browser versions, so the
      output is deterministic.
    - Add a `check-window-globals` mode (e.g. a `--check` flag) that regenerates
      in memory and exits non-zero if the name set differs from the committed
      file, printing the added and removed names.
    - Add a separate job to `.github/workflows/node-ci.yml`, outside the Node
      version matrix, that runs
      `npx playwright install --with-deps chromium firefox webkit` and then the
      check. A Playwright bump without regenerating the list then fails CI.
    - If the browsers can't launch, either mode fails with a message telling
      the developer to run that install command. No contributor doc currently
      lists build scripts (`build-schema` isn't documented anywhere), so document
      `build-window-globals` in the script's own header comment and in the
      generated file's header.
6. **Message**:

    > `location` is already a browser global, so Chapbook can't make this
    > variable available to JavaScript. `[if]` conditions, `[JavaScript]` and
    > vars-section values will see the browser's `location` instead; only
    > `{location}` inserts see your variable. Rename it to fix this.

    For Chapbook's own names, say "Chapbook built-in" instead of "browser
    global".

## Not in scope

- Changing what Chapbook indexes (ticket 05's option A stands). Undefined
  `location.reload()` in `[JavaScript]` drawing `VariableNeverSet` is
  accepted.
- Warning at JavaScript-context _uses_ of the variable.
- SugarCube: sigiled variables can't collide.

## Done when

- `location: 'cave'`, `Date: 1`, `passage.x: 1`, `location (a > 1): 2` and
  `engine.state.set('history', 1)` each produce one warning on the name (first
  segment for dotted names). `name: 'Bob'`, `loc: 1`, `config.x: 1`,
  `sound.x: 1` and `trail: []` produce none.
- The diagnostic can be disabled per passage and via `tt3.config.json`.
- `npm run build-window-globals` regenerates the list. A second run with the
  same browsers leaves the file unchanged. `npm run package` neither runs it
  nor needs browsers.
- The CI check passes on a fresh list and fails, naming the differences, when
  the committed list is edited.
- `npm test` green.
